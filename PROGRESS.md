## Build decisions
- Supabase project exists but is empty: built with the new-project rules on the existing ref, never recreated (Governor, 9 Oct 2026).
- PDF review pack generated in the browser, not a Netlify Function; spec bumped to v1.1 (Governor, 9 Oct 2026).
- profiles follows spec §5: role esg_lead is the admin (no separate admin flag); retired_at is the active state.
- profiles carries created_at ("added on" on the Users screen) and updated_by/updated_at like every other table (session 1).
- A resubmission keeps its project_code and takes version n+1; unique (project_code, version). A new project takes the next sequence value (session 1).
- project_history is written by a SECURITY DEFINER trigger (search_path '', schema-qualified) so no user ever needs an insert right on the history table; the change comment travels in the transaction setting app.change_comment, which the narrow functions set (session 1).
- The authenticated role has no DELETE or TRUNCATE grant on any table, on top of "no DELETE policy" (session 1).
- Reporting year = the portfolio as of the end of that year (status rebuilt from the status rows in project_history); the current year = as of today; actions exist in the current year only (session 1, session 2).
- "Both target lines" on the water intensity chart = the intensity target (−20 %) and the absolute target (−10 % withdrawal) expressed as intensity over the planned output (session 1).
- Water intensity, site missing a 2030 plan: output held flat at FY2024 and labelled estimate (spec §9); waste: a 2030 plan row with waste_total_t replaces the latest total as the denominator (session 1).
- The ESG lead registers group projects only; a site's projects are registered by the site (builder, 9 Oct 2026, spec v1.2); built as the insert policy in session 2.
- An Approved project is never edited in place: a change is a re-approval, a new version in Potential with the approved version Obsolete, out of every target figure until approved again; the ESG lead edits figures only while Pending approval (builder, 9 Oct 2026, spec v1.2); built as `reapprove_project` and `edit_project_figures` in session 2.
- Spec v1.2 was written by Claude Code from the builder's confirmed answers, not through the Tool Architect; the Project Governor iterated CLAUDE.md on it on 9 Oct 2026 (session 1).
- Chart palette is the brand's binding encoding (green approved, taupe pending, hatched gap or declined, grey anchors); because taupe and grey fail the dataviz contrast checks, every chart carries direct labels, a legend and the register as its table view (session 1).
- PDF fonts: Montserrat SemiBold/Bold and Source Sans 3 Regular/SemiBold TTFs (Google Fonts, OFL) in public/fonts/, loaded only when a pack is generated; jsPDF is loaded on demand so it stays out of the main bundle (session 1).
- Auth as built is the magic link of spec §6 (builder decision), not the framework's email-and-password default: no password, no Change password screen; identities are created by the admin-users function, the first one by the platform owner in the dashboard (Governor, 9 Oct 2026).
- Protected columns: the column triggers refuse a session write unless the transaction is marked by a narrow function (`app.narrow_function = on`, set with `set_config(..., true)` by `begin_narrow`) or there is no session (auth.uid() null: migrations and the admin function). One mechanism for every table, so a policy never has to list columns (session 2).
- A "no" on an update is a 0-row update (the policy does not reach the row), not an error; a "no" on an insert, a protected column or a transition is an error (42501). The screens show the error text; a 0-row update cannot happen from a screen because the button is not offered (session 2).
- Resubmit creates version n+1 immediately as a copy of the declined version (the function) and then opens the edit form; re-approval creates the copy and opens its project page. Either way the new version is Potential and editable by its owner; nothing is typed into a status (session 2).
- The ESG lead maintains sites and targets on the Reference data screen (value and years of a target; name, city, type and active of a site; a new site with its code); a renamed site that anything references is refused by the trigger, as the matrix says (session 2).
- The admin function's "create" also serves an existing profile that has no login yet (the seeded people, or a failed identity step): it creates the identity and changes nothing else; the Users screen offers it as "Create login" on such rows (session 2).
- Refusal test half A runs as SQL impersonation inside one rolled-back transaction because the sandbox cannot reach the project over HTTPS; the same checks the API would make (RLS, grants, triggers, function guards) are exercised, with `anon` and `authenticated` as the roles and the JWT claims set as PostgREST sets them (session 2).
- The demo portfolio was seeded with the history triggers paused so the fixture history rows are the only ones; from now on every write goes through the triggers (session 2).
- The workshop reset is a plain SQL script run by the platform owner in the SQL Editor (`supabase/demo-reset.sql`), not a database function: the builder asked for data ingestion only, nothing to build; the script keeps every login and every profile with a login, wipes the record tables, ingests the demo rows with their original ids and deletes the history rows the triggers write during the ingest, so the demo's own history is the only one (session 2).
- The admin function is reached at /api/admin-users through an explicit redirect in netlify.toml, listed before the SPA rule; the function's own URL stays the default one (session 2).
- A committee decision date is never after today, judged in Europe/Berlin (the company's day) by the function and capped in the dialog by the browser's local day (builder finding at half B, session 2).
- A target change carries its reason: `targets.change_comment` on the row, with updated_by and updated_at; the trigger refuses a session change without a fresh comment (blank, or the same text as the previous one). The dialog carries an attention box saying the change applies to the whole organisation. Matrix line 42 amended in place (no new rule, no new line). A full history table for targets is on the Backlog (builder finding at half B, session 2).
- The data store notifies subscribers after every reload; the app state bumps its version on that signal, so an action re-renders every screen without a refresh (builder finding at half B, session 2).
- Every action ends with a confirmation banner carrying the entries (builder, half B re-check): the screen calls notify() after the function returns, with the page the banner belongs to, so a banner survives the navigation an action makes (resubmit opens the edit form, re-approval the new version) and clears when the person leaves that page (session 2).
- The target warning is a pop-up with "I understand" and the button clicked a second time, by builder decision at the half B re-check; the reason stays required in the form, the database still refuses a change without a fresh reason (session 2).
- The project URL variable is `VITE_SUPABASE_DATABASE_URL`: that is the name the Netlify Supabase extension writes with the Vite preset (seen in the dashboard, 9 Oct 2026), not the `VITE_SUPABASE_URL` the spec assumed. The browser client and the admin function read the extension's name and accept the spec's name only as a local fallback; CLAUDE.md's variable line corrected to match (session 2).
